# Building the workflows (classify, people, and — after approval — emails)

Read the Clay plugin's `clay:workflows-cli` skill first for command syntax (nodes, edges,
conditionals, agent nodes, triggers, publish). This file says WHAT to build and which traps bit
us; that skill says HOW the CLI wants it. Templates are in `assets/nodes/` — every `<…_NODE_ID>`
placeholder is filled with the id `nodes create` returns.

## Why two workflows

A bulk run always enters at the trigger. If classification and people search were one workflow,
re-running people (to change titles, fix countries, split a capped company) would re-pay the
classifier for every company, and a non-deterministic model may disagree with the first answer.
So: **classify once**, save the CSV, then feed `Side` + `Classification` into a separate people
workflow as trigger inputs.

## What each action really costs (measured, Oct 2026)

Clay bills two things:
- **actions**: the search/enrichment allowance;
- **data credits**: the `credits balance`.

The catalog's "1 credit" label was wrong for several of these, so read `dataCreditsUsed` off a
draft test before quoting any price. Never quote from the catalog.

| Action | Measured | Note |
|---|---|---|
| Find People v2 (`cpj-find-lists-of-people-v2`) | 1 action, 0 data credits per search | the user's rule: "it just consumes actions and must not consume any credits" |
| Enrich Person (`cpj-enrich-person`, by LinkedIn URL) | 1 action, 0 data credits | |
| Enrich Company (`cpj-enrich-company-v2`) | 1 action, 0 data credits | by domain, or by `clay_company_id` |
| Claygent agent, `gpt-6-luna`, web search on | 1 action + 0.1 data credit per row | the API key is registered in Clay |
| Classifier agent (`gpt-4.1-mini`) | read it from the draft test | |
| Email waterfall + ZeroBounce | per provider plan | `references/email_workflow.md` |

Mining's full people run made 5,250 searches, all actions; the data-credit balance didn't move.
Every split adds one search per capped company per group.

## Workflow 1 — classify (costs credits per row)

```
Manual trigger (inputs = feed columns)
  → Build Company Record (code)          normalise; pick the best description
  → Has Domain? (conditional)  ─no→ Skipped - No Domain (code)
  → Enrich company (tool: cpj-enrich-company-v2, company_identifier = {{domain}})   1 credit
  → Classifier (agent, gpt-4.1-mini)     prompt from the user, labels = icp.yaml keys
  → Company Output (code)                returns Side + Classification + the enrichment fields
```

- **The bulk result is the LAST node's output only.** End with a `Company Output` code node that
  returns `Side`, `Classification` and every enrichment field the Salesforce file needs (Size,
  Type, Industry, Founded, Description, Annual Revenue, Company LinkedIn URL…). Without it the
  firmographics are computed, paid for and thrown away.
- **Enrich company v2 returns Sub-Industry, Primary Offerings and Business Stage only when looked
  up by DOMAIN** (`company_identifier_type: company_domain`). They sit under `derived_datapoints`
  (`subindustry[]`, `primary_offerings[]`, `business_stage`, plus `business_type`, `revenue_streams`,
  `pattern_tags`). A `clay_company_id` lookup omits that block, and the catalog schema doesn't list
  it (measured on Metso, 2026-10-25). `specialties[]` and `total_funding_amount_range_usd` come back
  either way. Cost measured: 1 action, 0 data credits. About 1 company in 4 has no derived data
  (e.g. Alcoa and BHP).
- **The company "is it new?" gate is NOT in the workflow.** It runs locally before the feed is
  sent (`supabase-known-lookup` skill, `companies` mode): a company that should not be paid for
  is simply absent from the feed, so no later mistake can reach it.
- **Interpolate the prompt inputs** (`{{description}}`, `{{company_domain}}`…). A bare
  `#INPUTS#` heading makes the model classify with no data and still answer confidently.
- Agent output schema, FLAT: `{"Side": {"type": "string", "description": "Exactly 'Buy Side' or
  'Sell Side'"}, "Classification": {"type": "string", "description": "Exact short label from the
  closed list"}}`. Templates: `classify_classifier_agent.json`, `classify_has_domain.json`,
  `classify_skip_no_domain.json`; the Highways Build code is in
  `references/classifier_prompt_example.md`.

## Workflow 2 — people (Find People is 0 credits; it uses the people-search allowance)

```
Manual trigger  inputs: Company Name, Domain, Side, Classification, Countries Override,
                        Seniority Group, Fit                       (people_trigger_inputs.json)
  → Build Company Record (code)                                    (people_build_record.json)
  → ICP Mapping (code, GENERATED by scripts/icp_mapping.py)
  → Searchable? ─no→ Skipped - Unmapped                            (people_searchable_gate / skip_unmapped)
  → Fit Keep?   ─no→ Skipped - Fit Filter                          (people_fit_gate / skip_fit)
  → Find People (tool: cpj-find-lists-of-people)                   (people_find_people.json)
```

- **Check the action key exists before building.** The Highways node uses
  `cpj-find-lists-of-people` (0 credits per search, measured), but by 2026-10-21 Clay's catalog
  only lists `cpj-find-lists-of-people-v2` ("Find contacts at company", catalog price 1 credit).
  Run `clay workflows actions list` and `actions schema e251a70e-46d7-4f3a-b3ef-a211ad3d8bd2
  <key>`; if only v2 exists, use it, compare its input names with `people_find_people.json`
  (v2 takes `company_identifier_type` and `company_identifier`), and read the real per-search cost
  off the draft test before quoting the people step as free.
- Find People settings that matter: `limit` 10 (the maximum with full profiles — 11+ is
  rejected), `identifiers_only` **false** (true allows 500 but drops first/last name and location,
  which Salesforce needs), `job_title_mode` contain (word-level: "PR" does not match "Project"),
  `job_title_seniority_match_mode` exact, `include_past_experiences` false.
- `location_countries_include` filters the **person's** location, not the company office.
- **Wire every optional input end to end**: trigger → Build `inputSchema` → Build output → ICP
  Mapping `inputSchema`. On Highways `Countries Override` sat in the feed for a month while the
  mapping node never received it. After building, run ONE draft test
  (`clay workflows runs test <wf> --inputs row.json`, then `runs get <wf> <run> --verbose`) and
  read the ICP Mapping outputs: countries, seniority and titles must be what you expect.
- The ICP Mapping node is generated from `icp.yaml` — never hand-edit it in Clay. Change the
  YAML, regenerate with `icp_mapping.py payload`, `nodes update`, test, publish.

## Workflow 3 — emails (only after the marketing manager approved the people list)

Generated, not hand-built: `scripts/email_workflow.py` creates the whole graph (Supabase lookup first;
Blitz → LeadMagic → Prospeo + ZeroBounce only for people Supabase has no email for; every paid answer
written back). Read `references/email_workflow.md` for the accounts, the build and the draft test.

## Both workflows — finishing

1. `clay workflows graph validate <wf>` — must be valid with no orphan nodes. Edges are not
   implied by `inputSchema`; wire them with `nodes update {"incomingEdges": [...]}` (a FULL
   replacement), branch edges carry the conditional's `ruleId`.
2. Draft test on 2–3 real rows, show the user the outputs, and only then
3. `clay workflows publish <wf> --name "v1 - …"` (numbered version; snapshots are the undo), then
4. `clay routines create workflow <wf> --name "<name>"` once (`--name` is required) — until then `runs start` answers `not_found`.
5. Bulk-run with `scripts/bulk_run.py` — `--plan`, then `--limit 1` (pilot), then the rest.

## Traps (each one cost real time or money once)

| Trap | Guard |
|---|---|
| `workflows create` makes an EMPTY workflow (no trigger) | create the trigger first; it produces the trigger NODE that inputSchema binds to |
| `outputSchema` written in the expanded JSON-Schema shape `nodes get` returns | write it FLAT `{name: {type, description}}` |
| A tool node's account set via node-level `authAccountId` | rejected or silently bound to another account; use `tools[0].appAccountId` and verify |
| Someone edits the draft in the Clay UI (e.g. sets limit 20) | diff the draft against the last published snapshot before every publish |
| `clay workflows actions test` | capped at 25/day per workspace — use draft `runs test` instead |
| ~1% of bulk rows `failed / Unknown error` | transient; `bulk_run.py --retry-failed` |
| Shared/hosted domains (`www.gov.uk`, `x.wixsite.com`) | `build_feed.py` flags them; fix the domain before the people run |
| Clay CLI on Windows | unsupported — `_clay.py` goes through WSL automatically |
| `ERROR_INVALID_INPUT` on a people row | a malformed domain (`.example.com`, `http:example.com`). Fix it, or drop it if it is a whole national government (`gob.pe`, `gouv.ci`) |
| Bulk row id over 64 characters | rejected by Clay; use a short stable id (`Row ID` = sha1[:16]). `bulk_run.py` refuses them |
| The local `bulk_run.py` died | Clay still runs every chunk already submitted, and bills them. Check `state.json` and the run before saying it stopped |
| A group came back full again (10) | split the group (B → B1 + B2) after asking; `collect.py capped --groups`, then `merge-splits` |
| A label with a comma in an unquoted YAML flow list | splits in two; `icp_mapping.py check --rules --scope` catches it |
